# Current Qwen3 / Jev / native vLLM implementation

[中文](implementation.zh-CN.md) · [README](../README.md) · [parameter examples](parameter_examples.md)

The active controller uses the Python `vllm.LLM` object. It keeps one engine loaded and calls `LLM.generate` once per segment. `engine` and `runtime` settings apply at startup; only selected `SamplingParams` values can change on the next segment. The model prompt, seed, `max_tokens`, and single output candidate remain runner-owned.

## Call sequence

1. `config.load_config` loads `config.json`, `parameters.json`, and `jev_questions.json`; `parameters.validate_parameters` checks types, bounds, and typed control metadata.
2. `backend.PythonBackend` tokenizes the user task with the Qwen chat template. `runner.execute` appends generated token IDs to the prompt before each new segment. It bounds `max_tokens` by the chunk, total generation budget, and context window.
3. `jev_requests.score_request` constructs JSON with four Score questions and `state={task, generated, recent, step}`. `adapters.parse_scores` validates and normalizes the returned score and probability distributions. Scores range from 0 to 1 after normalization; high repetition is worse.
4. `policy.Controller.decide` applies fixed-mode hold and the revert check. If another segment can run, adaptive mode calls `jev_requests.direction_request`: one type-specific Choice per currently adjustable field. Its state includes the new Score values and current parameter values, but no reference answer or remaining-token budget.
5. `jev_requests.value_request` creates exact legal values for any chosen operation that needs them. Numeric directions produce up to three values at one, two, and three steps inside the configured control window. Boolean flips and other single-target operations need no extra API call. `parse_choices` checks the returned option and full probability distribution; `Controller.commit` stages accepted values for the next segment.
6. The next round's `applied_parameters` and `generation_request` show what actually reached vLLM. `decision_will_execute=false` means the loop stopped before a proposal could run. Each round's cumulative `answer_snapshot` is also written as a labeled section in `answer.txt`.

The maximum is one Jev request per fixed segment and three per adaptive segment. There is no cap on requests or rounds; a run ends when the model stops or the context window is full. Each request and filtered response is saved in `result.json`; saved configuration redacts `jev.api_key`. Choice and Score confidence fields are not used or stored.

## Typed actions and limits

`jev_requests.py` derives operations from the declared type, not from hard-coded parameter names. Every listed parameter is included in native requests; removing its entry omits it, and the legacy per-entry `enabled` flag is rejected. Numerics offer keep/increase/decrease and use `control.window` and `control.denominator`. Nullable numerics use `control.enable_candidates` while `null`, then the same bounded step rule when active, with an additional disable-to-`null` action. Booleans offer keep or the opposite state. Enums use declared `choices`. Nullable strings, lists, and mappings expose set/add/remove/clear only when applicable. String and list additions require `control.candidates`; mapping additions require validated `control.entries`. Empty candidate sets make those fields hold-only. `control.adaptive=false` keeps an observation field fixed even while it remains in each native request.

The shipped 22 entries are a representative subset of the much larger [vLLM checklist taxonomy](vllm_catalog_taxonomy.md); checklist presence does not prove runtime support. At their initial values, 20 entries offer a direction Choice. Two token-ID fields (`stop_token_ids`, `allowed_token_ids`) remain hold-only pending reviewed candidates. Beyond numbers, booleans and enums, three entry kinds exist: `logit_bias` with labelled token groups, `repetition_detection` with reviewed presets, and `bad_words` with candidate words (see the [parameter guide](parameter_examples.md)). Some of the 20 are observation or output-format switches and are not answer-quality controls. This implementation supports the current `stage: completion` route, and `doctor` constructs the installed `SamplingParams` without loading the model. The output-kind strings are converted to native `RequestOutputKind` members before construction.

Revert counts consecutive declines of the weighted normalized utility across adjacent segments (no magnitude threshold) and, after `policy.revert.consecutive_declines` of them, restores the parameters that produced the best utility so far; it is skipped when the current parameters already are those. A parameter moved in the same direction `policy.limits.max_same_direction` times is not offered that direction again until it moves the other way, and a parameter answered keep `policy.dormancy.keep_streak` times in a row is not asked for the next `skip_rounds` rounds. It does not remove already generated tokens or prove that a particular parameter caused the change. Multiple changes in one round also complicate attribution. `fixed` still calls Jev for Score records; `compare` pairs fixed and adaptive by task and seed. Independent answer grading is not implemented, so `status: completed` does not mean the answer is correct.

## Restart from a checkpoint

Whenever Jev is called (fixed and adaptive, not baseline) and `policy.restart.enabled` is true, a long reasoning can be sent back. From round `first_check_round` (20) Jev answers one Choice: `continue`, or go back to the start or to any earlier checkpoint. A checkpoint is a point where Jev was asked and said `continue`; after a `continue` the next question comes `recheck_every` rounds later.

When Jev picks a checkpoint, everything after it is discarded (kept in `result.json` with `abandoned: true`), the parameters are those that were in effect there, and a fresh attempt of `difference.probe_rounds` rounds is generated with a new seed (`seed + step + 1000 × restarts`). A second Choice asks Jev whether the fresh attempt takes a different approach from the abandoned one; if it says `same_approach` the attempt is discarded and generated again, at most `difference.max_tries` times (the last one is then kept). After `max_restarts` restarts the run is no longer asked. All costs are recorded: `total_generated_tokens` counts every attempt, `wasted_tokens` the discarded ones, `restarts[]` the choices, probabilities and verdicts. `generated_token_count` and `answer.txt` describe the final attempt only.
